# 서브 에이전트 운영 지침 (토큰 효율, 2026-10-26 선생님 지시)

이후 모든 작업에 적용한다. 기존 기능·구조·저장·배포 절차와 사용자 요청의 우선순위는 그대로 둔다.

## 역할 (모델은 그대로)
- **1번 기획 (sonnet)**: 요청을 분석해 실제 고칠 항목만 정리. 관련 파일·함수만 조사. 우선순위와 담당 파일 지정. 검토 호출 필요성 판단. 코드 수정 금지, 전체 재분석·기존 문서 재조사 금지, 단순 작업을 크게 부풀리지 않는다.
- **2번 개발 (opus)**: 명세대로 고친다. 관련 파일과 직접 의존 코드만 조사. 정상 기능 보존. 바뀐 기능 중심으로 테스트. 요청 안 한 리팩터링·기능 추가 금지(제안으로만), 전체 파일 출력·전체 재검사 피함, 통과한 검증 반복 안 함.
- **3번 검토·발전 방향 (opus)**: 바뀐 부분만 검토. 역사(사실·맥락·인물·사건·출처), 퀘스트(진행 논리·교육 타당성), UI(가독성·사용성), 공통 엔진(회귀 위험). 실질 문제와 개선 방향만 짧게. 근거 약한 사실은 단정하지 않는다. 사소한 취향 제안 금지.

## 표준 작업 명세 (기획이 작성)
1. 수정 목표(한두 문장) 2. 수정 항목 3. 담당 파일(확인된 경로와 역할; 모르면 검색 범위만) 4. 완료 조건 5. 유지할 기능·금지 사항 6. 검증 방법(필요한 테스트만) 7. 검토 필요성(호출 여부·범위)
- 코드 전체나 긴 배경은 넣지 않는다. 명세 뒤 별도 기획 보고서 금지. 예상 못 한 의존이 나올 때만 보완.

## 검토 호출 기준
- 생략: 단순 문구, 범위가 분명한 UI 위치·크기, 단일 파일 단순 오류, 역사·퀘스트·공통 엔진에 영향 없는 변경.
- 선택: 캐릭터 행동·특정 장면 중간 규모 개선, 퀘스트 조건·대화 흐름, 학습 경험에 영향, 회귀 위험 있는 수정 → 해당 부분만 전달.
- 필수: 역사 사실(사건·인물·연도·대사·설명) 변경, 고증이 중요한 장면 새로 구현, 여러 장면에 영향 주는 공통 시스템, 데이터 구조·퀘스트·진행 구조 변경, 대규모 수정 → 바뀐 것과 관련된 부분만.
- 개발 중 새 위험이 보이면 개발이 검토를 요청할 수 있다.

## 작업 규모별 절차
- 소규모: 간단 명세 → 개발 → 해당 기능만 검증 → 검토 기본 생략.
- 중규모: 표준 명세 → 지정 범위 구현 → 관련 부분 검증 → 위험 있을 때만 검토.
- 대규모: 영향 범위 구체화 → 파일별 범위 분리 → 기능·회귀 검증 → 검토 → 여러 장면에 영향 있을 때만 넓은 검증.

## 파일·컨텍스트
- 같은 파일을 두 에이전트가 동시에 고치지 않는다. 고치는 동안 다른 에이전트는 읽기만. 파일별 담당자 명시.
- 필요한 부분만 읽고, 고친 뒤 diff로 요청 안 한 변경이 없는지 확인. 같은 문제 중복 조사 금지. 필요 없으면 추가 에이전트 안 띄움.
- 기존 문서·작업 기록 우선 활용. 단, 토큰 절약을 이유로 필수 확인·검증은 빼지 않는다.

## 보고 형식 (모든 에이전트)
완료 여부 / 변경한 파일 / 핵심 변경 사항 / 검증 결과 / 미해결 문제 / (필요할 때만) 중요한 개선 방향.
- 역사 검토는 출처와 확인 결과를 짧게. 확인 안 한 출처를 확인한 것처럼 쓰지 않는다.
- 개발 → 검토 전달은 소스 전체 대신 변경 파일·목적·핵심 변경점·검증 결과.

## 마치기
- 요청 기능 구현 + 필수 검증 통과 → 종료. 추가 개선은 제안으로만.
- 기록은 완료한 일·변경 파일·현재 상태·미해결 문제·다음 후보만. 컨텍스트가 길어지면 진행 상황을 남기고 새 세션에서 이어 간다.
